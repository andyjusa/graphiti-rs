# Same-Pi Rust read-path comparison — October 16, 2026

This is a comparison of deployed compatibility main `c1b501c` with the read-path and owned-property changes in `0ef0893`. It is separate from the October 15 Python/Rust comparison; do not combine measurements from the two cohorts.

## Results

**Median server CPU fell 6.6%, from 2.11 to 1.97 seconds per 300 measured requests.** Every paired round used less CPU. The final candidate passed the predeclared Pareto criteria. All 1,800 measured requests and 180 warmups completed, complete response hashes matched, and owned test containers/networks were removed.

| Server measurement | Baseline `c1b501c` | Candidate `0ef0893` |
| --- | ---: | ---: |
| CPU seconds per 300 requests, median (range) | 2.11 (2.07–2.12) | 1.97 (1.95–2.00) |
| Final RSS KiB, median (range) | 12,408 (12,160–12,524) | 12,292 (12,148–12,612) |
| Process peak RSS KiB, maximum of 3 rounds | 12,624 | 12,660 |
| Episode-read p50 ms, median (range) | 3.302 (2.632–3.321) | 2.457 (2.441–2.469) |
| Hybrid fact-search p50 ms, median (range) | 47.743 (47.743–47.761) | 47.295 (47.082–47.329) |
| Semantic node-search p50 ms, median (range) | 25.900 (25.732–26.070) | 25.296 (25.185–25.506) |

Ranges describe the three per-round measurements, not confidence intervals. Memory is essentially unchanged: median final RSS is 116 KiB lower, while maximum process peak RSS is 36 KiB higher. Episode latency varied across baseline rounds; these small sequential samples do not establish a general latency or tail-latency guarantee. CPU is the principal measured gain. Database and mock costs are excluded from the server figures and retained separately in the raw report.

## Fixed conditions

Both Rust executables were built with Rust 1.95 in Bookworm, with `graphiti-compat`, and checked against their source manifests and binary SHA256 hashes on the Pi. The same Pi4, disposable FalkorDB 4.16.6, 1,200 synthetic facts, 1,201 entities, 40 episodes and 3072-dimensional orthogonal mock vectors were used.

The preserved `bench-paired-pi.py` evaluator is imported without changes by `bench-rust-pi.py`. Each server is limited to one CPU and 768 MiB. The DB and mock have separate limits. Three rounds alternate baseline/candidate, candidate/baseline, baseline/candidate; every workload has ten warmups and 100 measured sequential requests with seed 20261015. Complete responses are timestamp-normalized and hashed. Server CPU, RSS and process peak RSS are distinguished from DB and mock cost.

Each execution has a prospective manifest and append-only lifecycle/result ledger in the owned root's `.autoresearch/` directory. The first two allocation-oriented comparisons used a predeclared 5% CPU threshold and were rejected. Before launching the separate direct-read comparisons, we declared `--acceptance pareto`: no more than 2% median CPU increase, 1 MiB median RSS increase or 10% regression in any workload's median-of-rounds p50; identical response hashes; no errors/OOM; unchanged protected files and successful cleanup. It requires either at least 5% lower median CPU, or at least 5% lower p50 in a workload with improvement in all three paired rounds. The original evaluator/data/requests are unchanged. Results from earlier policies are not relabelled.

## Changes under test

Compatibility reads issue `GRAPH.RO_QUERY` directly, avoiding a preceding `EXISTS`. A typical single-group indexed search drops from six Redis commands to three. Only the exact missing-graph `ERR` response is an empty result; wrong-type keys and other database failures remain errors. Dedicated Pi checks verify that absent reads do not create a graph and that string keys are left intact. Embedding JSON is deserialized by reference and compact vectors no longer need an intermediate `Vec<f32>`. Owned read results move their property maps into DTO decoding, removing a second copy of all returned vector values. Borrowed planning/audit entry points share the same normalization code. Missing columns now return errors instead of indexing past the row.

## Excluded connection-pooling candidate

An earlier candidate `d087d2c` additionally shared a provider HTTP client between ingestion and search. All requests and response hashes passed, and server CPU fell from 2.06 to 1.92 seconds per 300 requests. However, semantic node-search p50 rose from 26.04 to 68.04 ms. It failed the predeclared latency gate and was rejected. The shared-client change and its connection-specific assertion were removed; the tested read-path candidate retains main's connection behavior.

The repeated approximately 42 ms delay is observed evidence. A delayed-ACK interaction with the HTTP/1.1 mock is a hypothesis, not a packet-level diagnosis or a claim about the real Luna gateway. The original evaluator was kept unchanged. [Rejected measurements](pi-rust-20261016-rejected-pooling.json) are retained.

## Allocation-only candidate

A second candidate `51741d3` retained the connection behavior. Its median server CPU was 2.09 → 2.06 seconds per 300 requests (1.4% lower), with RSS 212 KiB higher and similar p50 latency. It also failed the predeclared 5% CPU threshold; this is not reported as a material performance gain. [Measurements](pi-rust-20261016-rejected-allocations.json) are retained. The next candidate removes the metadata cache and addresses the larger repeated Redis round trip while retaining the vector-copy changes.

## Direct-read-only candidate

A third candidate `2ef3dc8` removed redundant Redis existence checks and retained the vector-copy changes, without the metadata cache. All six runs passed the correctness and non-regression gates. Median CPU was 2.09 → 2.00 seconds per 300 requests (4.3% lower); episode p50 was 2.604 → 2.500 ms, fact search 47.936 → 47.349 ms and node search 26.098 → 25.537 ms. Final RSS was 12,172 → 12,176 KiB. This still missed the predeclared 5% improvement threshold and was rejected as a completed candidate. [Measurements](pi-rust-20261016-rejected-direct-read.json) are retained.

The separately built final candidate `0ef0893` also consumes owned database property maps instead of cloning them, including returned 3072-dimensional vectors, before DTO deserialization. It keeps the same read queries, fields and normalization. This is a new source comparison with a fresh baseline under the same Pareto policy; the third cohort is not relabelled.

## Scope and operations

These are synthetic retrieval measurements, not ingestion, real model inference, internet latency or whole-system memory results. No real provider API was called by the benchmark or regression tests. The Mac only coordinated builds and SSH; server execution and measurements ran on the Pi. The benchmark and regression tests did not write to production or change its credentials/provider configuration. The operating Pi still runs `c1b501c`; this report does not record a deployment. The tested read-path changes do not change the MCP schema, stored data, model or dimensions.

Reproduction requires Linux ARM64, both pinned image IDs, their full source commits, the original evaluator and the two build manifests. Create an owned mode-0700 `/home/pi4-3/graphiti-rust-bench-20261016-<suffix>` root, put `graphiti-rust-pi-20261016` in `OWNED`, stage the two scripts under `scripts/`, and put build manifests under `source-manifests/{baseline,candidate}.json`. Run `python3 scripts/bench-rust-pi.py --root ROOT --baseline-image sha256:BASELINE --candidate-image sha256:CANDIDATE --baseline-commit BASELINE_COMMIT --candidate-commit CANDIDATE_COMMIT --acceptance pareto`. Use the exact image IDs, hashes, source commits and per-round samples in the raw report. The coordinator rejects non-Pi execution and mismatched artifacts and removes only its labelled test resources.
