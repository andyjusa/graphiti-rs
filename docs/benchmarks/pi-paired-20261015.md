# Python Graphiti ↔ graphiti-rs: matched Pi4 retrieval benchmark

This comparison runs on the physical Raspberry Pi, not on a Mac, a desktop VM
or a remote cloud runner. It measures the preserved Python MCP server and the
currently deployed Rust release against the same disposable synthetic database.
It does not benchmark the latest Python 0.31 API or claim full-feature equivalence.

## Versions and scope

- Python: `graphiti-core 0.28.2`, the preserved ten-tool MCP wrapper and existing
  Falkor edge-read/group-routing patches. Its original source hashes and package
  versions are emitted by the benchmark entrypoint.
- Rust: source `8df990467bab7f2c53b0ab3fbbafa9ef7e7f9c4b`, the existing ARM64
  operational image and binary. This is the deployed release, rather than a
  rebuild of the later selected upstream backports on `main`.
- Both use real MCP HTTP handling and real DB retrieval. Generation is forbidden;
  fresh query embeddings make one HTTP request to the same local mock, which
  returns a known 3072-dimensional unit vector. No paid model calls or model
  weights are involved.
- Python uses its real registered tools, formatter, service and Graphiti search
  code. The test entrypoint replaces provider construction and private-config
  startup with a supplied client; it skips production re-embedding, telemetry and
  sitecustomize. It does not load an unused local model to inflate the baseline.
  Rust uses synthetic writable mode with an empty durable journal so it also
  performs fresh query embeddings. Neither receives ingestion work.

## Matched conditions

A fresh, internal Docker network hosts a DB container. App and mock containers
share only its network namespace; there are no published ports, original DB
mounts, credentials or routes. The Pi host sends HTTP directly to that private
container IP, using the same endpoint, request bodies, headers and client for
both servers. Each app runs alone; the production service remains running
separately and is excluded from these measurements.

| Setting | Both implementations |
| --- | --- |
| App CPU / memory | 1 CPU quota / 768 MiB; container swap disabled |
| DB | Same FalkorDB process, module 4.16.6; 1 CPU / 512 MiB |
| Data | 1,200 facts, 1,201 entities, 40 episodes |
| Embeddings | 3,072 dimensions; one orthogonal unit vector per person/fact |
| Indexes | Same operational node/relationship fulltext and node range indexes |
| Workloads | Exact episode read; hybrid fact search; semantic-only node search |
| Sampling | 100 sequential requests per workload after 10 warmups |
| Repetitions | 3 rounds, order Python/Rust → Rust/Python → Python/Rust |
| Result gate | One expected UUID plus identical complete canonical tool-response hashes |

A `markerNNNNNN` hybrid query matches both the lexical token and its unit vector.
A `semanticNNNNNN` node query has no lexical match and obtains that same vector
from the mock. Only its intended entity exceeds the semantic threshold. This
catches skipped semantic retrieval and incorrect empty responses while avoiding
undefined tied ranking among many equally similar candidates.

## Measurement interpretation

Server RSS and process peak RSS are `/proc/<pid>/status` `VmRSS` and `VmHWM`.
They include the Python interpreter and loaded libraries or the Rust process,
but exclude the separate DB, mock and client. DB RSS and CPU are recorded
separately after every workload. CPU seconds are deltas from `/proc/<pid>/stat`
over the 100 measured requests; idle CPU uses a two-second sample.

Reported median latency is measured end to end through HTTP/MCP, including the
mock request for search. Warmups are excluded. Full samples and per-round
percentiles are retained. The DB/cache is warm and shared across sequential
runs; alternating order reduces, but does not eliminate, order effects. CPU quota
does not pin a dedicated physical core. Startup time includes Docker and
readiness polling and is not advertised as pure language startup latency.

These are bounded synthetic retrieval results, not ingestion throughput,
large-corpus scaling, multilingual retrieval quality or an equivalent real LLM
workload. Server memory savings do not imply the same percentage saving for the
whole system: FalkorDB still consumes its own memory. Local-model weights and
real inference would add a separate budget to either implementation.

## Reproduction

The image IDs and source hashes in the result identify the exact preserved
runtime; the Python image is a retained deployment artifact, not a generally
available upstream image. Reproduction needs equivalent pinned Python/MCP
sources and the recorded patches. The benchmark refuses macOS and other
non-Linux/non-ARM64 hosts.

Stage [the coordinator](../../scripts/bench-paired-pi.py) and
[Python MCP test entrypoint](../../scripts/bench-python-mcp.py) under an owned,
mode-0700 `graphiti-paired-bench-20261015-*` directory on the Pi. Create an `OWNED`
file containing `graphiti-paired-pi-20261015`, then run the coordinator with
`--root` pointing to that directory under a bounded remote job. It generates
uniquely labelled containers and a synthetic passwd entry, with no HOME override.
It checks headroom between stages, fails on response/model-count disagreement,
retains partial JSON and logs, and removes only its own labelled resources.
