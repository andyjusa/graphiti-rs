## Retrieval change

The compatibility reader uses existing operational fulltext indexes for Entity(name,summary,group_id) and RELATES_TO(name,fact,group_id). It follows the observed Python driver sanitation, OR tokens, group scoping, 33 stopwords and token bound. Fulltext score order feeds RRF directly. Returned relationship endpoints are derived and validated without re-matching the edge UUID. Group/type predicates apply before the result bound. Reads neither create nor rebuild indexes. An absent/incomplete index retains the documented bounded substring fallback; metadata/query errors propagate.

FalkorDB constructs indexes asynchronously ([pinned primary source](https://github.com/FalkorDB/FalkorDB/blob/v4.16.6/src/index/indexer.c#L397)). An early 1200-fact read returned no indexed fact while its node was already found. The repeated fixture recorded the relationship index as `[Indexing] 41/1200: UNDER CONSTRUCTION` before `OPERATIONAL`. A present non-operational index now produces a retry error rather than misleading empty or partial results; status validation has a regression test. Empty/all-stopword input deliberately returns empty rather than Python's invalid empty expression. Custom index language/stopwords, equal-score ordering and concurrent drop/rebuild behavior are not certified by these fixtures.

Episode reads scan unique UUIDs in 128-row keyset pages and retain the bounded most recent set by parsed RFC3339 instant, then apply the global group limit. A 201-episode fixture proves a newer UTC instant outside the old lexical window is returned despite other timestamps having a later calendar date and +14:00 offset. A 30-second overall deadline fails with an error rather than returning a partial scan. This improves the old lexical-window behavior and increases DB scan work; arbitrary schemas, duplicate UUIDs, concurrent writers and full Python timestamp-order parity remain outside this evidence.
